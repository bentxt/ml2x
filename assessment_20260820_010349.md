# ml2java assessment

Assessment time: 2026-08-20 01:03:49 Europe/Zurich

## Overall assessment

`ml2java` is a strong compiler prototype with a sensible architecture and unusually good documentation, but it is not yet a dependable source-to-source compiler. It currently accepts some programs that produce incorrect results or invalid Java.

This is credible compiler work rather than a throwaway sketch. The architecture and written contract provide a good foundation. The main weakness is the boundary between “accepted by the checker” and “valid, meaning-preserving Java.” That boundary currently has several serious holes.

## Findings

### 1. Accepted programs can silently compute incorrect results

Three targeted programs compiled successfully under both `ml2java` and `javac`, but behaved incorrectly.

#### Nested options lose their meaning

`Some None : int option option` matched `None` instead of `Some _`.

Both values become Java `null` because options are erased completely in `src/emit_java.ml:237`, and `Some x` is emitted as only `x` at `src/emit_java.ml:530`. Nested options therefore cannot distinguish outer `None` from `Some None`.

#### Guards are incorrectly counted as exhaustive coverage

This match was accepted as exhaustive:

```ocaml
match true with
| true when false -> 7
| false -> 9
```

It returned `0`. Coverage is recorded before the checker considers whether an arm has a guard in `src/check.ml:724`. When every runtime condition fails, the generated program exposes the emitter's zero-initialized result temporary.

The compiler therefore silently invents a value instead of rejecting the match or reporting a failed match at runtime.

#### Boolean short-circuit evaluation is broken for statement-bearing operands

This expression executed its right-hand side:

```ocaml
false && (touched <- 1; true)
```

`touched` became `1`, although the right-hand side of `false && ...` must not execute. Statement-bearing operands are materialized before the Java boolean expression in `src/emit_java.ml:544`, breaking short-circuit evaluation.

These are semantic correctness problems, not cosmetic differences in generated Java.

### 2. Some accepted programs generate Java that `javac` rejects

Three cases were reproduced.

#### Statement-bearing top-level values

A declaration such as:

```ocaml
let answer = if true then 1 else 2
```

is accepted. The emitter writes the temporary declaration and `if` statement directly inside the Java class body, where statements are illegal. The relevant emission path begins at `src/emit_java.ml:966`.

#### Static methods can access instance fields

The checker gives static and instance methods the same class context at `src/check.ml:1043`. A static method can therefore refer to a field and generate code such as:

```java
return this.value;
```

`javac` rejects this because `this` does not exist in a static context.

#### Private or static methods can satisfy an interface check

The interface implementation check in `src/check.ml:1059` compares method name, arity, parameter types and return type. It does not require the implementation to be public and non-static.

A private method is consequently accepted as an interface implementation, after which `javac` rejects it for attempting to use weaker access privileges.

### 3. Generic functions are accepted but not emitted correctly

This source passed the `ml2java` checker:

```ocaml
let id (x : 'a) : 'a = x
let main () : unit = print_endline (string_of_int (id 3 + 1))
```

The generated `id` returned `Object`, so `javac` rejected `Object + long`.

Function parameter and return annotations are instantiated independently in `src/check.ml:641`, losing the fact that both occurrences of `'a` are the same type variable. The emitter maps the unresolved parameter to `Object` in `src/emit_java.ml:219`.

### 4. Arbitrary `-o` filenames can produce unusable Java files

Compiling:

```sh
ml2java Core.mlj -o Renamed.java
```

still produces `public final class Core`. `javac Renamed.java` rejects the file because a public `Core` class must be stored in `Core.java`.

The CLI permits an arbitrary output name in `bin/ml2java.ml:6`, while the generated class name always comes from the input basename in `src/emit_java.ml:1032`.

### 5. Some declaration errors have no useful source position

AST declarations do not retain source positions. The checker consequently uses the artificial position `0:0` at `src/check.ml:1016` for many duplicate declarations, type annotation errors, interface errors and method return errors.

The diagnostic format is consistent, but `file.mlj:0:0` cannot direct the reader to the faulty declaration.

The targeted assessment programs then established the failures described above. Those temporary source files were removed after testing.

## Strengths

- The lexer, parser, semantic checker and emitter are cleanly separated.
- `src/ast.ml` provides a clear contract between compiler phases.
- Recording the inferred type of every expression gives the emitter useful semantic information.
- The deliberately restricted language profile is a sound way to approach Java lowering.
- The generated Java is generally readable and has almost no runtime dependency.
- Mutability, function arity, constructor arity, member access and many unsupported source constructs receive explicit checks.
- `check.sh` performs a genuine compile, `javac`, execute and output-comparison path.
- `README.md` and `SPEC.md` explain the intended language and Java representation clearly.

## Test-suite limits

The suite is useful, but the four positive fixtures combine many features without covering difficult interactions. It says it covers guards, options, static methods and interfaces, but it does not cover guarded-only exhaustiveness, nested options, static access to instance state or private interface implementations.

The test driver also does not separately check the exit status of generated Java programs at `check.sh:31`. A Java program that prints the expected output and then exits with an exception could pass the output comparison.

There are no parser fuzz tests, checker property tests, or systematic tests asserting that every checker-accepted program also passes `javac`. Java keyword and duplicate-name handling also remain largely untested.

## Milestone judgment

The work demonstrates a complete end-to-end compiler pipeline rather than only a parser or emitter demonstration. The existing examples prove that the central approach works across records, variants, pattern matching, lists, tuples, mutable state and a limited object layer.

At the present milestone, it is best described as a convincing v1 research prototype. It is not yet safe to assume that an accepted program has valid Java output or preserves the source program's behavior.
